How this site works

An AI-assisted career system, built with Claude Code

This portfolio, and every resume I send, comes from one private, version-controlled bank of career evidence. AI agents interview me, draft, and tailor. Deterministic code checks their work. I approve anything that leaves the repo. This page covers how it works, how I built it, and how I keep it accurate.

The problem

After nearly a decade in security, my career history lived in about twenty resume and cover-letter files. Each tailored copy was a fork. The best phrasing of a win was often in a file from years ago, the numbers didn't always agree, and nothing told me which strengths I had evidence for and which I didn't.

Security work adds a second problem: much of it is confidential. What I can say in a resume to a hiring manager is not what I can say on a public web page, so every claim needs a public version and a private one, and nothing private can slip through.

The design: AI proposes, code verifies, I approve

The system splits the work by what each part is good at. Language models handle judgment over messy text. Plain Python handles every rule that must never be broken. I make every decision that matters.

Judgment Claude Code skills

Repeatable agent workflows checked into the repo, each with written instructions:

  • /ingest reads past resumes and builds the bank, merging the same win phrased five ways into one entry
  • /interview asks me one question at a time to fill gaps, pushing for scope and measurable results
  • /tailor maps a job posting's requirements to evidence and drafts a cited resume
  • /bank-review drafts sanitized public text for items I choose to publish
  • /publish previews the site and shows exactly what changes before it goes live

Rules The rmgr CLI

Deterministic Python with no AI in it. The agents call it; they can't argue with it.

  • Schema validation of every file (Pydantic models, exported as JSON Schema)
  • Gap analysis that ranks weak spots in the bank
  • Resume rendering to Word, PDF, Markdown and plain text
  • An ATS check: text round-trip, section order, two-page limit, keyword coverage
  • A leak guard that fails the site build if anything private appears

Decisions Me

  • I'm the only source of new facts. Agents record what I say, never what they infer.
  • I approve every public item, one at a time.
  • I confirm every estimated metric before it counts as verified.
  • I review the diff of every session before it's committed.

How it flows

  1. Sources

    Past resumes, cover letters, a LinkedIn export, and interview transcripts. Text is extracted so analysis is reproducible.

  2. /ingest + /interview

    Agents turn sources and my answers into structured entries, citing where each one came from.

  3. The bank

    One YAML file per accomplishment: the full story, metrics, skills, a visibility level, and its sources. Validated on every change.

  4. /tailor → resume

    A posting goes in; a two-page, ATS-checked resume comes out, with every bullet citing the bank entries behind it.

    /bank-review → this site

    Approved items only, rendered through the leak guard and deployed by GitHub Actions to a separate public repo.

A job-finder seam is already in place: anything that drops a posting file of the right shape into an inbox folder can feed /tailor, and the application log tells it which jobs I've already applied to.

Guardrails: keeping the AI honest

The biggest risk in using AI for a resume is that it writes something plausible and untrue. I treated the agents the way I'd treat any powerful, untrusted contributor: clear rules, least privilege, and checks they can't skip.

Never invent

The project rules forbid made-up metrics, titles, dates, tools, or scope. An unknown value is left empty and becomes a question for my next interview. Estimates I give are stored as unverified until I confirm them.

Every bullet cites its evidence

A tailored resume may rephrase a bank entry to match a posting's wording, but each bullet lists the entry ids it came from. The validator rejects a bullet with no source, or one that draws on a private item.

Gaps are reported, not papered over

When a posting asks for something the bank has no evidence for, /tailor says so plainly and offers a short targeted interview. Only my answers can close a gap.

Three visibility levels

Every item is public (this site, through a separately written public line), resume (tailored resumes only), or private (my reference only, never in any output).

A leak guard on every build

After rendering, the build scans every output file, including the PDF's extracted text, for contact details, non-public item ids, resume bullets, full stories, and anonymized employer names. One hit fails the build and deletes the output.

Confidentiality by default

Public text describes principles, not specific controls, and leaves out internal names and "before" numbers that would reveal a weakness in an employer's program. The agents are told to ask about visibility whenever an answer touches anything sensitive.

Securing the repo itself

A system that holds my contact details and confidential work history should be built like any other sensitive system.

  • Separation: the source of truth lives in a private repo; the public repo only ever receives built, leak-checked output.
  • Least-privilege deploys: publishing uses an SSH deploy key scoped to the one public repo, verified against GitHub's published host key, instead of a personal access token.
  • Secret scanning: gitleaks runs as a pre-commit hook and in CI over the full history.
  • Supply chain: every GitHub Action is pinned to a full commit SHA, only an allowlisted set of actions may run, dependencies are locked and audited with pip-audit, workflows are linted with zizmor, and Dependabot proposes updates weekly.
  • Public repo protection: secret scanning, push protection, and a ruleset that blocks force-pushes and deletion of main.

How I built it

I built this with Claude Code, Anthropic's agentic coding tool. I set the architecture, the rules, and the security requirements; Claude Code did most of the implementation, and I reviewed each change as it landed.

  1. Requirements interview. Before any code, Claude interviewed me on the decisions that mattered: one YAML file per accomplishment, a private source repo plus a public output repo, per-item visibility, and "rephrase but never invent." The answers became a written, phased build plan.
  2. Schema and validation first. The data model, a validation CLI, tests, and CI came before any AI workflow, so every later step had something strict to check against.
  3. Ingest. One session read about twenty past resumes and cover letters, built the role timeline, merged duplicates, and wrote a report of conflicts and missing numbers.
  4. Interviews and gap analysis. A ranked gap report drives each interview. The first session added a dozen new entries and strengthened seven more.
  5. Tailored resumes. ATS-safe rendering (single column, standard headings, text-based PDF) and an automated check of the output.
  6. Security hardening, then this site. CI hardening landed before anything was public. The portfolio, its leak guard, and the publish workflow followed.
  7. Application log and job-finder seam. A tracked stage for every application, plus a documented contract for future automation.

Each phase was its own branch and pull request with tests and green CI. Each session ended by updating the project's instruction file with what changed and what to do next, so the next session, a fresh agent with no memory, picked up exactly where the last one stopped.

How I maintain it

For each job
/tailor the posting, review the analysis and gap list, build and ATS-check the resume, then track the application's stage as it moves.
Every few months
A check-in interview to capture recent work while the details are fresh, and a gap interview when the gap report shows weak areas.
Quarterly
/bank-review to merge duplicates, refresh stale numbers, and decide whether anything new should go public.
Publishing
Merging a change to main rebuilds this site in GitHub Actions. The build fails closed if the leak guard finds anything.

Every working session is one commit with a prefix for its area (bank:, apply:, site:, tools:), so the history of the data folder reads as a history of my career.

Takeaways

  • Put the non-negotiables in code, not in the prompt. Instructions shape what an agent tries to do; validators and build gates decide what it can actually ship.
  • Make provenance mandatory. When every claim must cite its source, fabrication becomes a validation error instead of a judgment call.
  • Keep a human on the outward-facing actions. Agents draft freely inside the repo; publishing, committing, and anything public waits for my explicit approval.
  • Write the context down. Rules, conventions, and handoff notes in the repo make each new session productive immediately, and make the agents' behavior reviewable.

These are the same principles I'd bring to any team adopting agentic AI: clear contracts, least privilege, defense in depth, and auditable output.
